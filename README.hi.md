एक बहु-क्लॉड ऑपरेटिंग सिस्टम जो कर्मचारियों को नियुक्त करता है, कार्यों का मार्ग निर्धारित करता है, उनकी पुष्टि करता है और उन्हें 61 विशिष्ट भूमिका अनुबंधों के माध्यम से संचालित करता है। यह कार्य पैकेट बनाता है, स्कोर किए गए भूमिका मिलान से सही टीम को इकट्ठा करता है, निष्पादन से पहले टूटी हुई श्रृंखलाओं का पता लगाता है, जब कार्य अवरुद्ध या अस्वीकृत हो जाता है तो स्वचालित रूप से पुनर्प्राप्ति मार्ग निर्धारित करता है, और प्रत्येक निर्णय में संरचित प्रमाण की आवश्यकता होती है। इसमें गतिशील वितरण शामिल है जो बड़े पैमाने पर मिशनों के लिए अनुकूलित होता है - एक 10-घटक भंडार स्वचालित रूप से 28 ऑडिट चरणों में बदल जाता है, न कि 6।

## यह क्या करता है

रोल ओएस बहु-क्लॉड का उपयोग करने का पेशेवर तरीका है। यह उन विशिष्ट विफलताओं को रोकता है जो सामान्य एआई वर्कफ़्लो उत्पन्न करते हैं:

- **विचलन** - भूमिकाएँ अपनी सीमा में रहती हैं। उत्पाद पुनर्निर्मित नहीं होता है। फ्रंटएंड दायरे को फिर से परिभाषित नहीं करता है। बैकएंड उत्पाद दिशा का आविष्कार नहीं करता है।
- **गलत पूर्णता** - पूर्ण होने की परिभाषा ठोस है। वह कार्य जो अंतराल को छिपाता है, सत्यापन छोड़ देता है या किसी भिन्न समस्या को हल करता है, उसे अस्वीकार कर दिया जाता है।
- **संदूषण** - विभाजित या विरासत में मिली परियोजनाओं में पहचान अवशेष होते हैं। रोल ओएस शब्दावली, दृश्यों और मानसिक मॉडलों में क्रॉस-परियोजना विचलन का पता लगाता है और उसे अस्वीकार करता है।
- **भावना-आधारित प्रगति** - प्रत्येक हस्तांतरण संरचित होता है। प्रत्येक निर्णय प्रमाण से जुड़ा होता है। "यह पूरा हो गया लगता है" एक मान्य स्थिति नहीं है।

## यह कैसे काम करता है

अपने कार्य का वर्णन करें। रोल ओएस स्वचालित रूप से सही स्तर के समन्वय का निर्धारण करता है।

```bash
roleos start "fix the crash in save handler"
# → MISSION: Bugfix & Diagnosis (70% confidence)
#   Chain: Repo Researcher → Backend Engineer → Test Engineer → Critic Reviewer

roleos start "add a new export command"
# → PACK: Feature Build (50% confidence)
#   Roles: Orchestrator, Product Strategist, Spec Writer, Backend Engineer, Test Engineer, Critic Reviewer

roleos start "something completely novel"
# → FREE-ROUTING (10% confidence)
#   Hint: Create a packet and run `roleos route` for role-level routing
```

**बैकअप सीढ़ी:**

1. **मिशन** - जब कार्य एक सिद्ध आवर्ती वर्कफ़्लो (बग फिक्स, उपचार, सुविधा-शिपिंग, दस्तावेज़, सुरक्षा, अनुसंधान, विचार मंथन, गहन ऑडिट, परीक्षण) से मेल खाता है। ज्ञात भूमिका श्रृंखला, कलाकृति प्रवाह, वृद्धि शाखाएँ और ईमानदार-आंशिक परिभाषाएँ।
2. **पैकेज** - जब कार्य एक ज्ञात परिवार होता है लेकिन पूर्ण मिशन आकार नहीं होता है। 10 कैलिब्रेटेड टीम पैकेज स्वचालित चयन और बेमेल सुरक्षा के साथ।
3. **मुक्त रूटिंग** - जब कार्य नया, मिश्रित या अनिश्चित होता है। यह सभी 61 भूमिकाओं को पैकेट सामग्री के विरुद्ध स्कोर करता है और एक गतिशील श्रृंखला बनाता है।

यह प्रणाली कभी भी गलत अमूर्तता के माध्यम से कार्य करने के लिए मजबूर नहीं करती है। यह बताता है कि इसने प्रत्येक स्तर क्यों चुना और विकल्प प्रदान करता है।

**सक्रिय निष्पादन के लिए एक आदेश:**

```bash
roleos run "fix the crash in save handler"
# → Created run: run-1234
# → Entry: MISSION (bugfix)
# → Started step 0: Repo Researcher → diagnosis-report
# → Guidance: Required sections: entrypoints, module-map, build-test-commands

roleos next                    # Start the next step
roleos complete diagnosis.md   # Complete the active step with artifact
roleos explain                 # Show full run state and guidance
roleos resume                  # Continue an interrupted run
roleos report                  # Generate completion report
roleos friction                # Measure operator touches
```

**जब चीजें गलत हो जाती हैं तो हस्तक्षेप:**

```bash
roleos retry 0                 # Retry a failed step
roleos reroute 1 "Frontend Developer" "UI bug"  # Swap a role
roleos escalate "Test Engineer" "Repo Researcher" "missed edge case" "re-diagnose"
roleos block 2 "waiting for API spec"
roleos reopen 0 "found issue in review"
```

निष्पादित कार्य डिस्क पर बने रहते हैं (`.claude/runs/`), इसलिए बाधित सत्र सुचारू रूप से फिर से शुरू होते हैं। प्रत्येक चरण में ऑपरेटर मार्गदर्शन शामिल होता है: क्या उत्पन्न करना है, आवश्यक अनुभाग और समाप्ति शर्तें।

**एक बार रूट किए जाने के बाद:**

1. **प्रत्येक भूमिका एक हस्तांतरण उत्पन्न करती है** - संरचित आउटपुट जिसमें प्रमाण आइटम होते हैं जो अगली भूमिका के लिए अस्पष्टता को कम करते हैं।
2. **आलोचक अनुबंध के विरुद्ध समीक्षा करता है** - स्वीकार करता है, अस्वीकार करता है या संरचित प्रमाण के आधार पर अवरुद्ध करता है, न कि धारणा के आधार पर।
3. **पुनर्प्राप्ति मार्ग स्वचालित रूप से निर्धारित होते हैं** - अवरुद्ध या अस्वीकृत कार्य को एक कारण, पुनर्प्राप्ति प्रकार और आवश्यक कलाकृति के साथ सही समाधानकर्ता तक रूट किया जाता है।

## बजट-जागरूक वितरण

रोल ओएस प्रत्येक वितरण चरण के लिए स्थानीय **टोकन बजट विश्लेषक** से परामर्श कर सकता है और घोषणा में एक सलाहकार व्यय पूर्वानुमान संलग्न कर सकता है - वैकल्पिक (`ROLEOS_BUDGET_CONSULT`), सलाहकार (यह कभी भी वितरण को अवरुद्ध नहीं करता है), और एक निर्धारित आधार पर विफल-खुला। डिफ़ॉल्ट रूप से बंद; पूर्वानुमान स्थानीय है और चलाने के लिए स्वतंत्र है। [हैंडबुक](https://mcp-tool-shop-org.github.io/role-os/handbook/specialist-budget/) देखें।

## टूल-कॉल निरीक्षण

रोल ओएस `PreToolUse` सीम पर टूल कॉल को सत्यापित और गेट करता है - निर्धारणात्मक रूप से, बिना किसी मॉडल के साथ जो हॉट पाथ में है:

- **अनुरूपता वॉचर** (सलाहकार, विफल-खुला) - एक निर्धारित स्कीमा + संगणनीय-अनुबंध फर्श एक प्रस्तावित कॉल की तुलना इसके कैटलॉग किए गए टूल-अनुबंध से करता है और एक *सिद्ध* गैर-अनुरूप कॉल पर एक सलाहकार निर्णय संलग्न करता है; यह कभी भी अवरुद्ध नहीं होता है। एक वैकल्पिक एलएलएम छत (`ROLEOS_CONFORMANCE_CONSULT`) वास्तव में-सिमेंटिक अवशेष को संभालती है।
- **क्षमता गेट** (विफल-बंद, वैकल्पिक `ROLEOS_CAPABILITY_GATE`, डिफ़ॉल्ट रूप से बंद) - *अपरिवर्तनीय* कार्यों पर निर्धारित न्यूनतम विशेषाधिकार (एनपीएम/पाइपी प्रकाशित करें, `gh release`, `git push`, भंडार संपादन, पृष्ठों को तैनात करें)। एक गेटेड कार्रवाई तब तक अस्वीकार कर दी जाती है जब तक कि निर्देशक ने `.claude/role-os/capabilities.json` में इसकी क्षमता प्रदान नहीं की हो, इसलिए एक गलत कदम - एक ईमानदार गलती या एक इंजेक्ट किया गया - अनधिकृत अपरिवर्तनीय कार्रवाई को ट्रिगर नहीं कर सकता है। नामित-क्षतिपूर्ति नियम के लिए निवारक पूरक। [हैंडबुक](https://mcp-tool-shop-org.github.io/role-os/handbook/) देखें।

## क्रू की फ़ाइल

प्रत्येक भूमिका के लिए एक **फ़ाइल** होती है—यह एक चरित्र शीट होती है जो रन-टाइम कॉन्फ़िगरेशन के रूप में भी काम करती है। छह क्षमताएँ (दृढ़ता, गति, दायरा, संशयवाद, स्वायत्तता, स्पष्टवादिता) वास्तविक नियंत्रणों से जुड़ी होती हैं; आठ प्रकार की **स्वभाव** परत (संशयवादी, निर्माता, अन्वेषक, विद्रोही...) व्यवहार संबंधी निर्देश देती है; और प्रत्येक भूमिका में एक चित्रित चित्र और एक ग्रेड होता है। पूरी क्रू को गैलरी के रूप में ब्राउज़ करें (`dossier/dossier.html`)—प्रत्येक भूमिका का रडार उसके आदर्श से तुलना करते हुए उसकी समायोजित संरचना दिखाता है।

जब किसी भूमिका में फ़ाइल होती है, तो डिस्पैच एक **परिचालन मुद्रा** जोड़ता है—यह स्वभाव का व्यवहार संबंधी निर्देश और भूमिका की क्षमताओं से एक मुद्रा पंक्ति होती है—इसलिए शीट वास्तव में उस भूमिका को कॉन्फ़िगर करती है। वैकल्पिक और अतिरिक्त: जिन भूमिकाओं में फ़ाइल नहीं है, वे पहले की तरह ही व्यवहार करती हैं। [हैंडबुक](https://mcp-tool-shop-org.github.io/role-os/handbook/crew-dossier/) देखें।

## संगठनात्मक रोलआउट स्थिति

संगठन-व्यापी रोलआउट स्थिति (कतार, निर्णय, ऑडिट रिकॉर्ड, प्रति-रिपॉजिटरी लॉक पैकेट) एक अलग **निजी**, संगठन-आंतरिक रिपॉजिटरी (`role-os-rollout`) में मौजूद है। यह रिपॉजिटरी उत्पाद है; वह रिपॉजिटरी परिचालन स्थिति है।

## स्मृति और निरंतरता

रोल ओएस स्मृति परत का स्वामित्व या डुप्लिकेट नहीं करता है। जहां क्लॉड प्रोजेक्ट मेमोरी मौजूद है, यह कैनोनिकल निरंतरता प्रणाली है - भंडार तथ्य, निर्णय, खुले लूप और उपचार इतिहास वहां रहते हैं।

रोल ओएस क्लॉड प्रोजेक्ट मेमोरी के साथ एकीकृत होता है। यह इसे प्रतिस्थापित नहीं करता है।

## पूर्ण उपचार और शिपचेक

पूर्ण उपचार एक कैनोनिकल 7-चरण प्रोटोकॉल है जिसे क्लॉड प्रोजेक्ट मेमोरी में परिभाषित किया गया है (`memory/full-treatment.md`)। रोल ओएस भूमिका अनुबंधों, हस्तांतरणों और आलोचक गेट्स का उपयोग करके उपचार को रूट और समीक्षा करता है - यह प्रोटोकॉल को फिर से परिभाषित नहीं करता है।

**शिपचेक** 31-आइटम गुणवत्ता गेट है जो पूर्ण उपचार से पहले चलता है। किसी भी उपचार शुरू होने से पहले कठोर गेट A-D पास होने चाहिए। कैनोनिकल संदर्भ: `memory/shipcheck.md`।

क्रम: सबसे पहले शिपचेक, फिर पूर्ण उपचार। बिना कठोर गेटों को पास किए कोई v1.0.0 नहीं।

प्रत्येक भूमिका में एक पूर्ण अनुबंध होता है: मिशन, उपयोग कब करें, उपयोग कब न करें, अपेक्षित इनपुट, आवश्यक आउटपुट, गुणवत्ता मानक और एस्केलेशन ट्रिगर। प्रत्येक भूमिका को रूट किया जा सकता है - `roleos route` पैकेट सामग्री के आधार पर उनमें से किसी की भी सिफारिश कर सकता है।

## त्वरित शुरुआत

```bash
# Install (puts `roleos` on your PATH):
npm install -g role-os

# Scaffold the role spine into your repo:
roleos init
# (one-off alternative without installing: `npx role-os init`,
#  then prefix every command below with `npx role-os` instead of `roleos`)

# Describe what you need — Role OS picks the right level:
roleos run "fix the crash in save handler"
# → Creates run, picks bugfix mission, starts first step with guidance

# Step through:
roleos next                    # Start next step
roleos complete artifact.md    # Complete with artifact
roleos explain                 # Show full state
roleos report                  # Completion report

# Deep audit:
roleos audit manifest --generate   # Create audit-manifest.json
roleos audit                       # Start component-level deep audit
roleos audit status                # Check audit progress
roleos audit verify                # Verify manifest and outputs

# Dogfood swarm:
roleos swarm manifest --generate   # Auto-detect domains from repo structure
roleos swarm                       # Start multi-pass convergence swarm
roleos swarm status                # Check swarm progress by stage
roleos swarm findings              # List findings by severity
roleos swarm approve               # Approve feature gate

# Or go manual:
roleos start "fix the crash"   # Entry decision only (no run)
roleos packet new feature
roleos route .claude/packets/my-feature.md
roleos review .claude/packets/my-feature.md accept

# Explore missions and packs:
roleos mission list
roleos packs list
```

## रोल ओएस का उपयोग कब न करें

- सिंगल-लाइन सुधार, टाइपो या स्पष्ट बग
- बिना परिभाषित आउटपुट के अन्वेषणात्मक अनुसंधान
- वह कार्य जो 5 मिनट में किसी एक व्यक्ति के दिमाग में फिट हो जाए
- आपातकालीन हॉटफ़िक्स जिन्हें समीक्षा श्रृंखला पूरी होने से पहले शिप करने की आवश्यकता होती है
- वे परियोजनाएं जहां आप संरचना पर गति चाहते हैं

## सबूत

रोल ओएस को दो संरचनात्मक रूप से भिन्न रिपोज़िटरी में तीन परीक्षण आकृतियों में साबित किया गया:

**परीक्षण 001 - फ़ीचर कार्य** (क्रू स्क्रीन, स्टार फ्रेट)
- 7-भूमिका श्रृंखला, 45 परीक्षण परिदृश्य, 0 भूमिका टकराव
- फोर्क पूर्वज से संदूषण को रोका, इनलाइन आविष्कार को पकड़ा, ईमानदार बाधाओं को उजागर किया

**परीक्षण 002 - एकीकरण कार्य** (कैंपेनस्टेट वायरिंग, स्टार फ्रेट)
- 5-भूमिका श्रृंखला, बिना किसी फॉलबैक झूठ के वास्तुशिल्प सीम का समाधान किया
- एंटी-फॉलबैक परीक्षणों से यह साबित हुआ कि लाइव पथ वास्तविक है, न कि केवल एक प्लेसहोल्डर

**परीक्षण 003 - पहचान कार्य** (संदूषण शुद्धिकरण, स्टार फ्रेट)
- 6-भूमिका श्रृंखला, 51 परीक्षण परिदृश्य जिसमें टिकाऊ सीआई संदूषण रक्षा शामिल है
- व्यापक पुनर्निर्माण में ढहने के बिना विरासत में मिली काल्पनिक विचलन को ठीक किया

**पोर्टेबिलिटी परीक्षण** (पर्सोना स्थिरता, सेंसर-हास्य)
- समान रीढ़, अलग भाषा/डोमेन/स्टैक
- केवल संदर्भ परिवर्तनों के साथ अपनाया गया - कोई मूल अनुबंध संशोधन नहीं

**पूर्ण उपचार FT-001** (पोर्टलाइट-डेस्कटॉप)
- ट्रीटमेंट पैक भूमिकाओं के साथ 7-चरण वाला स्टाफ उपचार
- शिपचेक गेटिंग सिद्ध, शून्य भूमिका टकराव

**पूर्ण उपचार FT-002** (स्टूडियोफ्लो)
- समान उपचार पैक, संरचनात्मक रूप से भिन्न रिपो (रचनात्मक कार्यक्षेत्र बनाम गेम)
- ट्रीटमेंट पैक पोर्टेबल - कोई अनुबंध संशोधन आवश्यक नहीं

**ब्रेनस्टॉर्म गोल्डन रन** (एमसीपी सर्वर मार्केटप्लेस विषय)
- 9-भूमिका श्रृंखला, समानांतर में 4 विश्लेषक, क्रॉस-जांच + विवाद ग्राफ का खंडन करें
- 4 चुनौतियां जारी की गईं, 3 दावों को संकुचित किया गया, 1 अनसुलझा - स्वस्थ दबाव, गतिरोध नहीं
- प्रस्तुत कलाकृतियों से सत्य-परत परमाणुओं तक 16+ ट्रेस लिंक
- पूर्ण श्रृंखला की हिरासत सिद्ध: सत्य → परमाणु → विवाद → संश्लेषण → विस्तार → न्यायाधीश → प्रस्तुत करें → ट्रेस करें

## सुरक्षा

डिफ़ॉल्ट रूप से, रोल ओएस केवल **स्थानीय फ़ाइल सिस्टम** पर काम करता है। यह मार्कडाउन टेम्पलेट की प्रतिलिपि बनाता है और आपके रिपॉजिटरी की `.claude/` निर्देशिका में पैकेट/निर्णय/रन फाइलें लिखता है। डिफ़ॉल्ट संचालन कोई नेटवर्क अनुरोध नहीं करता है, किसी भी गुप्त जानकारी को संभालता नहीं है, और कोई टेलीमेट्री एकत्र नहीं करता है। कोई खतरनाक संचालन नहीं — सभी फ़ाइल लेखन डिफ़ॉल्ट रूप से स्किप-इफ-एग्ज़िस्ट का उपयोग करते हैं।

तीन **वैकल्पिक** सुविधाएँ तब नेटवर्क को स्पर्श करती हैं जब आप उन्हें स्पष्ट रूप से सक्षम करते हैं:

- **`roleos verify-citations`** — यह बाहरी `prism` CLI पर कमांड भेजता है, जो सार्वजनिक arXiv/Crossref API के विरुद्ध उद्धरण पहचानकर्ताओं को हल करता है (सत्यापित किए जा रहे उद्धरण आईडी/URL भेजता है)।
- **विशेषज्ञ स्तर** (`roleos specialist`, पंजीकृत भूमिकाएँ) — `.role-os/specialists.json` में आपके द्वारा कॉन्फ़िगर किए गए `backend_url` पर डिस्पैच संकेतों को POST करता है (आमतौर पर एक स्थानीय मॉडल एंडपॉइंट)।
- **बजट / अनुरूपता परामर्श** (`ROLEOS_BUDGET_CONSULT` / `ROLEOS_CONFORMANCE_CONSULT`) — यह चरण/उपकरण-कॉल संदर्भ को HTTP के माध्यम से एक स्थानीय मॉडल पर सलाहपूर्ण निर्णय के लिए भेजता है।

तीनों डिफ़ॉल्ट रूप से बंद हैं और स्थानीय नियतात्मक व्यवहार में विफल रहते हैं। पूरी नीति के लिए [SECURITY.md](SECURITY.md) देखें।

| **Mission runner** | रन बनाएं, ट्रैक किए गए स्थिति के साथ चरणों से गुजरें, ईमानदार रिपोर्टिंग के साथ पूरा/असफल करें। अवरुद्ध-चरण प्रसार, श्रृंखला से बाहर वृद्धि चेतावनियाँ, अंतिम-चरण पुन: खोलना। | ✓ शिप किया गया |

| **Dogfood Swarm** | बहु-पास अभिसरण: तीन स्वास्थ्य चरण (बग/सुरक्षा → सक्रिय → मानवीकरण) फिर सुविधा पास। विशेष फ़ाइल स्वामित्व, प्रत्येक लहर के बाद निर्माण गेट, उपयोगकर्ता चेकपॉइंट। डोमेन ऑटो-डिटेक्शन मैनिफेस्ट उत्पन्न करता है। साक्ष्य पुल डोगफूड-लैब्स तक। | ✓ शिप किया गया |

### ब्रेनस्टॉर्म मिशन

"एआई ब्रेनस्टॉर्मिंग" नहीं। ब्रेनस्टॉर्म मिशन **कानून के तहत विशेष भूमिकाएँ हैं, जिसमें पता लगाने योग्य असहमति और निर्णायक परिणाम-असर वाला आउटपुट होता है।**

```bash
roleos run "explore product directions for a developer tool discovery platform"
# → MISSION: Brainstorm (Structured Inquiry)
#   Chain: 4 Analysts (parallel) → Normalize → Cross-Examine → Rebut → Synthesize → Expand → Judge
```

**यह अलग कैसे है:**

- **लेयर 1 (सत्य):** चार विश्लेषक भूमिका-देशी स्कीमा (संदर्भ मानचित्र, उपयोगकर्ता मूल्य मानचित्र, यांत्रिकी मानचित्र, स्थिति मानचित्र) उत्सर्जित करते हैं - साझा गद्य नहीं। प्रत्येक भूमिका अंधापन-प्रबलित है: निषिद्ध वाक्यांश, निषिद्ध दावा प्रकार, फ़िल्टर किए गए इनपुट विभाजन। परमाणुओं में उत्पत्ति होती है। एक निर्देशित क्रॉस-परीक्षा ग्राफ लक्षित चुनौतियाँ उत्पन्न करता है। मूल विश्लेषक दबाव के तहत बचाव करते हैं, संकुचित करते हैं या वापस लेते हैं।

- **लेयर 2 (रेंडर):** पांच विशिष्ट मानव आवाजें (सीमा ज्ञापन, फील्ड नोट्स, सिस्टम स्केच, दावा संक्षिप्त, क्रॉस-परीक्षा प्रतिलेख) जिसमें शाब्दिक प्रतिबंध होते हैं जो आवाज अभिसरण को रोकते हैं। संश्लेषण सत्य का उपभोग करता है, कभी भी प्रस्तुत गद्य नहीं। दोनों परतें हमेशा उपलब्ध होती हैं।

- **अभिपालन श्रृंखला:** प्रत्येक प्रस्तुत वाक्य सत्य-परत परमाणु पर वापस जाता है। संश्लेषण दिशाएँ परमाणुओं का हवाला देती हैं। क्रॉस-परीक्षा वास्तविक दावा आईडी को लक्षित करता है। विवाद ग्राफ उत्पाद है, गद्य नहीं।

**सिद्ध:** v0.4 गोल्डन रन - पूरी श्रृंखला की अभिपालन सत्यापित। संपूर्ण कलाकृति श्रृंखला के लिए [`examples/golden-run.md`](examples/golden-run.md) देखें।

### गहन ऑडिट मिशन

सतही स्कैन नहीं। गहन ऑडिट मिशन **रिपो को बाध्य घटकों में विघटित करता है और रिपो के अपने निर्भरता ग्राफ द्वारा निर्धारित पैमाने पर विशेषज्ञ ऑडिटर भेजता है।**

```bash
roleos run "deep audit this repo" --manifest=audit-manifest.json
# → MISSION: Deep Audit (Manifest-Scaled)
#   Steps: Component Auditor ×6 + Test Truth Auditor ×6 + Seam Auditor ×8 + Synthesizer + Action Plan + Critic = 23 steps
```

**यह अलग कैसे है:**

- **गतिशील प्रेषण** - कार्यकर्ता गणना निश्चित नहीं है। 10-घटक रिपो जिसमें 5 सीमा क्लस्टर हैं, 28 चरण उत्पन्न करते हैं (2×10 + 5 + 3)। 3-घटक रिपो 12 उत्पन्न करता है। स्केलिंग सूत्र `2N + K + 3` है जहाँ N = घटक, K = सीमाएँ।
- **मैनिफेस्ट-समर्थित पार्सल** - एक `audit-manifest.json` घटकों (फ़ाइल पथों, पंक्ति गणनाओं, विवरण के साथ) और सीमाओं (इंटरफ़ेस विवरण के साथ/से) को परिभाषित करता है। प्रत्येक ऑडिटर को केवल अपना पार्सल प्राप्त होता है।
- **चार भूमिका पुरातत्व** - घटक ऑडिटर (प्रति मॉड्यूल कोड सत्य), परीक्षण सत्य ऑडिटर (जो साबित करते हैं बनाम जो मौजूद हैं), सीम ऑडिटर (निर्भरता ग्राफ से एकीकरण सीमाएँ), ऑडिट सिंथेसाइज़र (सभी पार्सलों से रैंक किया गया निर्णय + कार्य योजना)।
- **प्रत्येक चरण पर कलाकृति सत्यापन** - `validateArtifact()` दोनों निष्पादन पथों में प्रत्येक चरण पूर्ण होने पर फायर करता है। परिणाम चरण वस्तुओं से जुड़े होते हैं। सिस्टम जानता है कि क्या प्रत्येक कलाकृति ने अपने अनुबंध को पूरा किया।
- **ईमानदार आंशिक** - जब बजट या दायरा पूर्णता को अवरुद्ध करता है, तो प्रति-घटक निष्कर्ष व्यक्तिगत रूप से मान्य होते हैं। सिस्टम जो कुछ भी पूरा हुआ उससे संश्लेषित होता है, कभी भी पूर्ण कवरेज का दिखावा नहीं करता है।

**सिद्ध:** रनर-देशी प्रमाणन रन - वास्तविक मैनिफेस्ट के खिलाफ 18 परीक्षण, वृद्धि पुन: खोलने और आंशिक विफलता सहित संपूर्ण जीवनचक्र सत्यापित। स्केलिंग सूत्र 3/6/10/15-घटक मैनिफेस्ट के लिए सत्यापित।

### डोगफूड स्वार्म मिशन

यह एक एकल-चरण लिंटर नहीं है। डॉगफूड स्वार्म मिशन **एक बहु-चरण अभिसरण प्रोटोकॉल चलाता है जो किसी रिपॉजिटरी को "काम करता है" से "उत्पादन के लिए तैयार" स्थिति में तीन स्वास्थ्य चरणों और पुनरावृत्तीय सुविधा वितरण के माध्यम से ले जाता है।**

```bash
roleos swarm
# → MISSION: Dogfood Swarm (Multi-Pass Convergence)
#   Stages: Health-A → Health-B → Health-C → Feature → Final
#   Domain agents: 3-5 parallel per wave (exclusive file ownership)
```

**यह अलग कैसे है:**

- **तीन-चरण स्वास्थ्य जांच** — चरण ए बग और सुरक्षा मुद्दों को ठीक करता है (जब तक 0 गंभीर + 0 उच्च मुद्दे न हों, तब तक दोहराएं)। चरण बी सक्रिय रूप से सुधार लागू करता है (उपयोगकर्ता निष्कर्षों की समीक्षा करते हैं)। चरण सी कोडबेस को उपयोगकर्ता के अनुकूल बनाता है - त्रुटि संदेश जो उपयोगकर्ताओं की मदद करते हैं, पुन: कनेक्शन प्रतिक्रिया, लोडिंग स्थिति, पहुंच क्षमता। प्रत्येक चरण एक अलग दृष्टिकोण है, यह एक ही स्कैन का दोहराव नहीं है।
- **अनन्य फ़ाइल स्वामित्व** — प्रत्येक डोमेन एजेंट `swarm-manifest.json` के माध्यम से विशिष्ट फ़ाइलों का मालिक होता है। कोई भी दो एजेंट एक ही फ़ाइल को संपादित नहीं करते हैं। कोई विलय संघर्ष नहीं। कोई समन्वय ओवरहेड नहीं।
- **बिल्ड गेट्स** — लिंट + टाइपचेक + टेस्ट, प्रत्येक चरण के बाद सफल होना चाहिए। सिस्टम स्वचालित रूप से बिल्ड सिस्टम (नोड, रस्ट, पायथन, गो) का पता लगाता है और सही कमांड चलाता है।
- **उपयोगकर्ता चेकपॉइंट** — स्वास्थ्य-बी और सुविधा जांच को निष्पादन से पहले स्पष्ट उपयोगकर्ता अनुमोदन की आवश्यकता होती है। सिस्टम निष्कर्ष प्रस्तुत करता है, उपयोगकर्ता यह तय करता है कि क्या बनाना है।
- **पुनरावृत्तीय अभिसरण** — चरण तब तक दोहराते हैं जब तक कि निकास शर्तें पूरी नहीं हो जातीं या अधिकतम पुनरावृत्तियों तक नहीं पहुंच जाते। प्रत्येक चरण पिछले सुधारों द्वारा पेश किए गए मुद्दों को पकड़ने के लिए शुरुआत से फिर से ऑडिट करता है।
- **डोमेन ऑटो-डिटेक्शन** — `roleos swarm manifest --generate` रिपॉजिटरी प्रकार (सीएलआई, वेब, डेस्कटॉप, एमसीपी, मोनोरेपो) का पता लगाता है और गैर-अतिव्यापी डोमेन असाइनमेंट उत्पन्न करता है।
