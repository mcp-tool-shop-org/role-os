एक रेपो-नेटिव ऑपरेटिंग लेयर जो 61 विशिष्ट भूमिका अनुबंधों के माध्यम से कर्मचारियों, मार्गों, मान्यताओं और कोडिंग-एजेंट कार्यों को चलाती है। यह कार्य पैकेट बनाता है, स्कोर किए गए भूमिका मिलान से सही टीम को इकट्ठा करता है, निष्पादन से पहले टूटी हुई श्रृंखलाओं का पता लगाता है, जब कार्य अवरुद्ध या अस्वीकृत हो जाता है तो स्वचालित रूप से पुनर्प्राप्ति मार्ग निर्धारित करता है, और प्रत्येक निर्णय में संरचित प्रमाण की आवश्यकता होती है। इसमें मैनिफेस्ट-स्केल्ड मिशनों के लिए गतिशील वितरण शामिल है - एक 10-घटक रेपो स्वचालित रूप से 28 ऑडिटर चरणों में बदल जाता है, न कि 6।

क्लॉड कोड एडाप्टर शिप (`roleos init` स्केफोल्ड `.claude/`)। अनुबंध मार्कडाउन हैं, जिन्हें कोई भी कोडिंग हार्नेस उपयोग कर सकता है - यह रेपो यह दावा नहीं करता है कि एक दूसरा एडाप्टर पहले से ही चल रहा है।

## यह क्या करता है

रोल ओएस कोडिंग-एजेंट कार्यों को व्यवस्थित करने का पेशेवर तरीका है। यह उन विशिष्ट विफलताओं को रोकता है जो सामान्य एआई वर्कफ़्लो उत्पन्न करते हैं:

- **विचलन** - भूमिकाएँ अपनी सीमा में रहती हैं। उत्पाद फिर से डिज़ाइन नहीं करता है। फ्रंटएंड दायरे को फिर से परिभाषित नहीं करता है। बैकएंड उत्पाद दिशा का आविष्कार नहीं करता है।
- **गलत पूर्णता** - पूर्णता की परिभाषा ठोस है। वह कार्य जो अंतराल को छिपाता है, सत्यापन को छोड़ देता है, या किसी भिन्न समस्या को हल करता है, उसे अस्वीकार कर दिया जाता है।
- **संदूषण** - फोर्क या विरासत में मिली परियोजनाओं में पहचान अवशेष होते हैं। रोल ओएस शब्दावली, दृश्यों और मानसिक मॉडलों में क्रॉस-प्रोजेक्ट विचलन का पता लगाता है और उसे अस्वीकार कर देता है।
- **भावना-आधारित प्रगति** - प्रत्येक हैंडऑफ़ संरचित होता है। प्रत्येक निर्णय प्रमाण से जुड़ा होता है। "यह पूरा हो गया है" एक मान्य स्थिति नहीं है।

## यह कैसे काम करता है

अपने कार्य का वर्णन करें। रोल ओएस स्वचालित रूप से सही स्तर के समन्वय का निर्णय लेता है।

```bash
roleos start "fix the crash in save handler"
# → MISSION: Bugfix & Diagnosis (70% confidence)
#   Chain: Repo Researcher → Backend Engineer → Test Engineer → Critic Reviewer

roleos start "add a new export command"
# → PACK: Feature Build (50% confidence)
#   Roles: Orchestrator, Product Strategist, Spec Writer, Backend Engineer, Test Engineer, Critic Reviewer

roleos start "something completely novel"
# → FREE-ROUTING (10% confidence)
#   Hint: Create a packet and run `roleos route` for role-level routing
```

**बैकअप सीढ़ी:**

1. **मिशन** - जब कार्य एक सिद्ध आवर्ती वर्कफ़्लो (बगफिक्स, उपचार, सुविधा-शिप, दस्तावेज़, सुरक्षा, अनुसंधान, विचार-मंथन, गहन-ऑडिट, डॉगफूड-स्वार्म) से मेल खाता है। ज्ञात भूमिका श्रृंखला, कलाकृति प्रवाह, वृद्धि शाखाएँ और ईमानदार-आंशिक परिभाषाएँ।
2. **पैक** - जब कार्य एक ज्ञात परिवार होता है लेकिन पूर्ण मिशन आकार नहीं होता है। 10 कैलिब्रेटेड टीम पैक, स्वचालित चयन और बेमेल गार्ड के साथ।
3. **मुक्त रूटिंग** - जब कार्य नया, मिश्रित या अनिश्चित होता है। यह सभी 61 भूमिकाओं को पैकेट सामग्री के विरुद्ध स्कोर करता है और एक गतिशील श्रृंखला को इकट्ठा करता है।

यह प्रणाली कभी भी कार्य को गलत अमूर्तता के माध्यम से मजबूर नहीं करती है। यह बताता है कि इसने प्रत्येक स्तर को क्यों चुना और विकल्प प्रदान करता है।

**सक्रिय निष्पादन के लिए एक कमांड:**

```bash
roleos run "fix the crash in save handler"
# → Created run: run-1234
# → Entry: MISSION (bugfix)
# → Started step 0: Repo Researcher → diagnosis-report
# → Guidance: Required sections: entrypoints, module-map, build-test-commands

roleos next                    # Start the next step
roleos complete diagnosis.md   # Complete the active step with artifact
roleos explain                 # Show full run state and guidance
roleos resume                  # Continue an interrupted run
roleos report                  # Generate completion report
roleos friction                # Measure operator touches
```

**जब चीजें गलत हो जाती हैं तो हस्तक्षेप:**

```bash
roleos retry 0                 # Retry a failed step
roleos reroute 1 "Frontend Developer" "UI bug"  # Swap a role
roleos escalate "Test Engineer" "Repo Researcher" "missed edge case" "re-diagnose"
roleos block 2 "waiting for API spec"
roleos reopen 0 "found issue in review"
```

कार्य डिस्क पर बने रहते हैं (`.claude/runs/`), इसलिए बाधित सत्रों को साफ-सुथरा तरीके से फिर से शुरू किया जाता है। प्रत्येक चरण में ऑपरेटर मार्गदर्शन शामिल होता है: क्या उत्पन्न करना है, आवश्यक अनुभाग और समाप्ति शर्तें।

**एक बार रूट किए जाने के बाद:**

1. **प्रत्येक भूमिका एक हैंडऑफ़ उत्पन्न करती है** - संरचित आउटपुट जिसमें प्रमाण आइटम होते हैं जो अगली भूमिका के लिए अस्पष्टता को कम करते हैं।
2. **आलोचक अनुबंध के विरुद्ध समीक्षा करते हैं** - संरचित प्रमाण के आधार पर स्वीकार, अस्वीकार या अवरुद्ध करते हैं, न कि धारणा के आधार पर।
3. **पुनर्प्राप्ति मार्ग स्वचालित रूप से निर्धारित होते हैं** - अवरुद्ध या अस्वीकृत कार्य को एक कारण, पुनर्प्राप्ति प्रकार और आवश्यक कलाकृति के साथ सही समाधानकर्ता को रूट किया जाता है।

## बजट-जागरूक वितरण

रोल ओएस प्रत्येक वितरण चरण के लिए एक स्थानीय **टोकन बजट विश्लेषक** से परामर्श कर सकता है और मैनिफेस्ट से एक सलाहकार व्यय पूर्वानुमान संलग्न कर सकता है - वैकल्पिक (`ROLEOS_BUDGET_CONSULT`), सलाहकार (यह कभी भी वितरण को अवरुद्ध नहीं करता है), और एक निर्धारित आधार रेखा पर विफल-खुला। डिफ़ॉल्ट रूप से बंद; पूर्वानुमान स्थानीय है और चलाने के लिए स्वतंत्र है। [हैंडबुक](https://mcp-tool-shop-org.github.io/role-os/handbook/specialist-budget/) देखें।

## टूल-कॉल निरीक्षण

रोल ओएस `PreToolUse` सीम पर टूल कॉल को सत्यापित और गेट करता है - नियतात्मक रूप से, बिना किसी मॉडल के हॉट पाथ पर:

- **अनुरूपता वॉचर** (सलाहकार, विफल-खुला) - एक नियतात्मक स्कीमा + कम्प्यूटेशनल-अनुबंध तल एक प्रस्तावित कॉल की तुलना इसके कैटलॉग किए गए टूल-अनुबंध से करता है और एक *सिद्ध* गैर-अनुरूप कॉल पर एक सलाहकार निर्णय संलग्न करता है; यह कभी भी अवरुद्ध नहीं करता है। एक वैकल्पिक एलएलएम छत (`ROLEOS_CONFORMANCE_CONSULT`) वास्तव में-सिमेंटिक अवशेष को संभालता है।
- **क्षमता गेट** (विफल-बंद, वैकल्पिक `ROLEOS_CAPABILITY_GATE`, डिफ़ॉल्ट रूप से बंद) - *अपरिवर्तनीय* कार्यों (एनपीएम/पाइपी प्रकाशित करें, `gh release`, `git push`, रेपो संपादन, पेज तैनात करें) पर नियतात्मक न्यूनतम-अधिकार। एक गेटेड कार्रवाई को तब तक अस्वीकार कर दिया जाता है जब तक कि निदेशक ने `.claude/role-os/capabilities.json` में इसकी क्षमता प्रदान नहीं की है, इसलिए एक गलत कदम - एक ईमानदार गलती या एक इंजेक्ट की गई गलती - एक अनधिकृत अपरिवर्तनीय कार्रवाई को ट्रिगर नहीं कर सकता है। नामित-क्षतिपूर्ति नियम का निवारक पूरक। [हैंडबुक](https://mcp-tool-shop-org.github.io/role-os/handbook/) देखें।

## क्रू डोजियर

प्रत्येक भूमिका में एक **डोजियर** होता है - एक चरित्र शीट जो रन-टाइम कॉन्फ़िगरेशन के रूप में भी काम करती है। छह योग्यताएं (कठोरता, गति, दायरा, संशयवाद, स्वायत्तता, ईमानदारी) वास्तविक वितरण नॉब्स पर मैप करती हैं; एक आठ-आर्केटाइप **स्वभाव** परत (संशयवादी, बिल्डर, अन्वेषक, मावेरिक...) एक व्यवहारिक निर्देश ले जाती है; और प्रत्येक भूमिका में एक चित्रित चित्र और एक ग्रेड होता है। पूरी क्रू को एक गैलरी के रूप में ब्राउज़ करें (`dossier/dossier.html`) - प्रत्येक भूमिका का रडार इसकी आदर्श आदर्श के विरुद्ध इसके ट्यून किए गए निर्माण को दिखाता है।

जब किसी भूमिका में एक डोजियर होता है, तो वितरण एक **ऑपरेटिंग मुद्रा** इंजेक्ट करता है - स्वभाव का व्यवहारिक निर्देश प्लस भूमिका की योग्यताओं से एक मुद्रा पंक्ति - इसलिए शीट वास्तव में भूमिका को कॉन्फ़िगर करती है। वैकल्पिक और योज्य: बिना डोजियर वाली भूमिकाएँ बिल्कुल पहले की तरह व्यवहार करती हैं। [हैंडबुक](https://mcp-tool-shop-org.github.io/role-os/handbook/crew-dossier/) देखें।

## संगठनात्मक रोलआउट स्थिति

संगठन-व्यापी रोलआउट स्थिति (कतार, निर्णय, ऑडिट रिकॉर्ड, प्रति-रेपो लॉक पैकेट) एक अलग **निजी**, संगठन-आंतरिक रेपो (`role-os-rollout`) में रहती है। यह रेपो उत्पाद है; वह रेपो परिचालन स्थिति है।

## स्मृति और निरंतरता

रोल ओएस मेमोरी परत का स्वामित्व या डुप्लिकेट नहीं करता है। जहां एक हार्नेस प्रोजेक्ट-मेमोरी स्टोर मौजूद है, यह कैनोनिकल निरंतरता प्रणाली है - रेपो तथ्य, निर्णय, खुले लूप और उपचार इतिहास वहां रहते हैं।

रोल ओएस जब मौजूद हो तो उस स्टोर के साथ एकीकृत होता है। यह इसे प्रतिस्थापित नहीं करता है।

## पूर्ण उपचार और शिपचेक

पूर्ण उपचार एक मानक 7-चरण प्रोटोकॉल है जिसे स्टूडियो प्रोजेक्ट मेमोरी में परिभाषित किया गया है (`memory/full-treatment.md`)। रोल ओएस, रोल अनुबंधों, हैंडऑफ़ और क्रिटिक गेट्स का उपयोग करके भूमिकाओं को रूट करता है और उपचारों की समीक्षा करता है - यह प्रोटोकॉल को फिर से परिभाषित नहीं करता है।

**शिपचेक** एक 31-आइटम गुणवत्ता गेट है जो पूर्ण उपचार से पहले चलता है। किसी भी उपचार को शुरू करने से पहले हार्ड गेट A-D को पास करना होगा। मानक संदर्भ: `memory/shipcheck.md`।

क्रम: पहले शिपचेक, फिर पूर्ण उपचार। हार्ड गेट्स को पास किए बिना v1.0.0 नहीं।

प्रत्येक भूमिका में एक पूर्ण अनुबंध होता है: मिशन, उपयोग कब करें, उपयोग कब न करें, अपेक्षित इनपुट, आवश्यक आउटपुट, गुणवत्ता बार और वृद्धि ट्रिगर। प्रत्येक भूमिका रूट करने योग्य है - `roleos route` पैकेट सामग्री के आधार पर उनमें से किसी की भी सिफारिश कर सकता है।

## त्वरित शुरुआत

```bash
# Install (puts `roleos` on your PATH):
npm install -g role-os

# Scaffold the role spine into your repo:
roleos init
# (one-off alternative without installing: `npx role-os init`,
#  then prefix every command below with `npx role-os` instead of `roleos`)

# Describe what you need — Role OS picks the right level:
roleos run "fix the crash in save handler"
# → Creates run, picks bugfix mission, starts first step with guidance

# Step through:
roleos next                    # Start next step
roleos complete artifact.md    # Complete with artifact
roleos explain                 # Show full state
roleos report                  # Completion report

# Deep audit:
roleos audit manifest --generate   # Create audit-manifest.json
roleos audit                       # Start component-level deep audit
roleos audit status                # Check audit progress
roleos audit verify                # Verify manifest and outputs

# Dogfood swarm:
roleos swarm manifest --generate   # Auto-detect domains from repo structure
roleos swarm                       # Start multi-pass convergence swarm
roleos swarm status                # Check swarm progress by stage
roleos swarm findings              # List findings by severity
roleos swarm approve               # Approve feature gate

# Or go manual:
roleos start "fix the crash"   # Entry decision only (no run)
roleos packet new feature
roleos route .claude/packets/my-feature.md
roleos review .claude/packets/my-feature.md accept

# Explore missions and packs:
roleos mission list
roleos packs list
```

## रोल ओएस का उपयोग कब न करें

- सिंगल-लाइन फिक्स, टाइपो या स्पष्ट बग
- बिना परिभाषित आउटपुट के अन्वेषणात्मक अनुसंधान
- वह कार्य जो 5 मिनट में किसी एक व्यक्ति के दिमाग में फिट हो जाए
- आपातकालीन हॉटफिक्स जिन्हें समीक्षा श्रृंखला पूरी होने से पहले शिप करने की आवश्यकता है
- ऐसे प्रोजेक्ट जहां आप संरचना से अधिक गति चाहते हैं

## सबूत

रोल ओएस को दो संरचनात्मक रूप से भिन्न रिपोज़ में तीन परीक्षण आकृतियों में साबित किया गया:

**परीक्षण 001 - सुविधा कार्य** (क्रू स्क्रीन, स्टार फ्रेट)
- 7-भूमिका श्रृंखला, 45 परीक्षण परिदृश्य, 0 भूमिका टकराव
- फोर्क पूर्वज से संदूषण को रोका, इनलाइन आविष्कार को पकड़ा, ईमानदार अवरोधों को उजागर किया

**परीक्षण 002 - एकीकरण कार्य** (कैंपेनस्टेट वायरिंग, स्टार फ्रेट)
- 5-भूमिका श्रृंखला, बिना किसी फॉलबैक झूठ के वास्तुशिल्प सीम को हल किया
- एंटी-फॉलबैक परीक्षणों ने साबित किया कि लाइव पथ वास्तविक है, न कि एक प्लेसहोल्डर

**परीक्षण 003 - पहचान कार्य** (संदूषण शुद्धिकरण, स्टार फ्रेट)
- 6-भूमिका श्रृंखला, 51 परीक्षण परिदृश्य जिसमें टिकाऊ सीआई संदूषण रक्षा शामिल है
- व्यापक पुनर्निर्माण में ढहने के बिना विरासत में मिली काल्पनिक विचलन को ठीक किया

**पोर्टेबिलिटी परीक्षण** (पर्सोना स्थिरता, सेंसर-हास्य)
- समान रीढ़, अलग भाषा/डोमेन/स्टैक
- केवल संदर्भ परिवर्तनों के साथ अपनाया गया - कोई मुख्य अनुबंध संशोधन नहीं

**पूर्ण उपचार FT-001** (पोर्टलाइट-डेस्कटॉप)
- उपचार पैक भूमिकाओं के साथ 7-चरण वाला स्टाफ उपचार
- शिपचेक गेटिंग सिद्ध, शून्य भूमिका टकराव

**पूर्ण उपचार FT-002** (स्टूडियोफ्लो)
- समान उपचार पैक, संरचनात्मक रूप से भिन्न रिपो (रचनात्मक कार्यक्षेत्र बनाम गेम)
- उपचार पैक पोर्टेबल - कोई अनुबंध संशोधन आवश्यक नहीं

**विचार मंथन का सुनहरा दौर** (एमसीपी सर्वर मार्केटप्लेस विषय)
- 9-भूमिका श्रृंखला, 4 विश्लेषक समानांतर में, क्रॉस-एग्जामिन + खंडन विवाद ग्राफ
- 4 चुनौतियाँ जारी की गईं, 3 दावों को संकुचित किया गया, 1 अनसुलझा - स्वस्थ दबाव, गतिरोध नहीं
- प्रस्तुत कलाकृतियों से सत्य-परत परमाणुओं तक 16+ ट्रेस लिंक
- श्रृंखला की पूरी कस्टडी सिद्ध: सत्य → परमाणु → विवाद → संश्लेषण → विस्तार → जज → प्रस्तुत → ट्रेस

## सुरक्षा

डिफ़ॉल्ट रूप से, रोल ओएस केवल **स्थानीय फ़ाइल सिस्टम** पर काम करता है। यह मार्कडाउन टेम्पलेट की प्रतिलिपि बनाता है और आपके रिपॉजिटरी की `.claude/` निर्देशिका में पैकेट/निर्णय/रन फ़ाइलें लिखता है। डिफ़ॉल्ट संचालन कोई नेटवर्क अनुरोध नहीं करता है, कोई गुप्त जानकारी नहीं रखता है, और कोई टेलीमेट्री एकत्र नहीं करता है। कोई खतरनाक संचालन नहीं - सभी फ़ाइल लेखन डिफ़ॉल्ट रूप से स्किप-इफ-एग्जिस्ट का उपयोग करते हैं।

तीन **ऑप्ट-इन** सुविधाएँ हैं जो तब नेटवर्क को छूती हैं जब आप उन्हें स्पष्ट रूप से सक्षम करते हैं:

- **`roleos verify-citations`** - यह बाहरी `prism` सीएलआई पर शेल करता है, जो सार्वजनिक arXiv/Crossref एपीआई के खिलाफ उद्धरण पहचानकर्ताओं को हल करता है (सत्यापित किए जा रहे उद्धरण आईडी/यूआरएल भेजता है)।
- **विशेषज्ञ स्तर** (`roleos specialist`, पंजीकृत भूमिकाएँ) - यह `.role-os/specialists.json` में आपके द्वारा कॉन्फ़िगर किए गए `backend_url` को डिस्पैच प्रॉम्प्ट पोस्ट करता है (आमतौर पर एक स्थानीय मॉडल एंडपॉइंट)।
- **बजट / अनुरूपता परामर्श** (`ROLEOS_BUDGET_CONSULT` / `ROLEOS_CONFORMANCE_CONSULT`) - यह एक सलाहकार निर्णय के लिए एक स्थानीय मॉडल को एचटीटीपी पर चरण/टूल-कॉल संदर्भ भेजता है।

तीनों डिफ़ॉल्ट रूप से बंद हैं और स्थानीय नियतात्मक व्यवहार के लिए खुले रहते हैं। पूरी नीति के लिए [SECURITY.md](SECURITY.md) देखें।

## रेसिपी कार्ड, जूरी और पैक कैलिब्रेशन

एक प्रशिक्षित समीक्षक उतना ही अच्छा होता है जितना कि उसने जिस डेटा से सीखा है। रोल ओएस उस डेटा को एक रेसिपी कार्ड पर रिकॉर्ड करता है, समीक्षकों के एक पैनल को मापता है, और एक पूर्ण रन को पैक चयन को बढ़ावा देने देता है। इनमें से कोई भी मॉडल को नहीं बुलाता है। समान फ़ाइल और समान सीड समान संख्याएँ उत्पन्न करते हैं।

### रेसिपी कार्ड

`roleos recipe` एक कार्ड की जाँच करता है (`roleos-recipe-card/v1`)। नौ मानक नियंत्रण प्रत्येक उस तरीके की रक्षा करते हैं जिससे एक समीक्षक अच्छा दिख सकता है, बिना अपने गुणों को सीखे। बिना माप के पास किया गया नियंत्रण एक अंतर है। एक असंगत माप एक त्रुटि है। `shuffled-labels` को विधि `balanced-permutation` का उपयोग करना होगा। `same-generator-no-error`: जब दोनों संपादन विधियों को रिकॉर्ड किया जाता है और उनके अंतराल ओवरलैप नहीं करते हैं, तो स्थिति `unresolved` होनी चाहिए, या जाँच विफल हो जाती है। `reversed-correction` केवल तभी पास होता है जब इसकी सटीकता का अंतराल पूरी तरह से 0.5 से ऊपर हो।

```bash
roleos recipe check starter-pack/examples/auditor-recipe-card.json
```

वह फ़ाइल एक भरी हुई सिंथेटिक कार्ड है, न कि एक प्रशिक्षित समीक्षक। जाँच प्रिंट करता है:

```
✓ starter-pack/examples/auditor-recipe-card.json (auditor-v1, role Auditor)
  note     controls[2] (shuffled-labels): permutation floor is 1/20; a pass at this floor means the observed result beat every null
  controls 9/9 standard controls passed
  sha256   5763c4dd57fc9f7bea41186493e56b72ce73a5e30f4c5c813248655a360b1588
```

नोट एक तथ्य है, अंतर नहीं। `roleos specialist register` `--recipe` लेता है और कार्ड के आईडी और हैश को उस संस्करण पर पिन करता है। [हैंडबुक](https://mcp-tool-shop-org.github.io/role-os/handbook/recipe-cards/) देखें।

### जूरी

`roleos jury select` केवल तभी एक पैनल रखता है जब एक नेस्टेड समूह-क्लस्टर्ड अंतराल कहता है कि पैनल सर्वश्रेष्ठ एकल समीक्षक को हरा देता है। अन्यथा, निर्णय यह समीक्षक है, या `insufficient-data` 30 आइटम या 10 समूहों से नीचे। एक समीक्षक जिसका कार्ड विफल या अनसुलझा मानक नियंत्रण है, उसे तब तक बाहर रखा जाता है जब तक कि `--allow-unproven` न हो। बिना कार्ड वाला समीक्षक अभी भी बैठा रहता है जब तक कि `--require-recipe` न हो। स्कोर कभी भी उलट नहीं होते हैं। समान सीड समान संख्याएँ दोहराता है।

```bash
roleos jury select starter-pack/examples/jury-validation.json --seed 0
```

इस सिंथेटिक फ़ाइल पर निर्णय `best-single (echo)` है। इको और शार्प एक ही गलतियाँ करते हैं, इसलिए त्रुटि स्थिरता 1.0000 है और डुप्लिकेट फ़्लैग उन्हें नाम देते हैं। फ़्लैग किसी भी समीक्षक को नहीं हटाता है। नेस्टेड अंतराल [-0.1000, 0.0000] है। यह 0 को छूता है, इसलिए यह पूरी तरह से 0 से ऊपर नहीं है, और यहां तक कि --आउट के साथ भी यह कोई पैनल फ़ाइल नहीं लिखेगा, क्योंकि --आउट केवल एक पैनल निर्णय के लिए एक लिखता है। [हैंडबुक](https://mcp-tool-shop-org.github.io/role-os/handbook/jury/) में पूरी रिपोर्ट है।

### पैक कैलिब्रेशन

जब एक रन समाप्त होता है, तो रोल ओएस एक परिणाम पंक्ति जोड़ता है। समान रन आईडी दूसरी पंक्ति नहीं लिखता है। एक पैक में कम से कम 5 रिकॉर्ड किए गए परिणाम होने के बाद, प्रत्येक पूर्ण रन जिसमें 0 सुधार हैं, उस पैक में +0.5 जोड़ता है, जिसकी अधिकतम सीमा +2 है। बढ़ावा कभी भी किसी ऐसे पैक को नाम नहीं देता है जिससे कीवर्ड पहले से मेल नहीं खाते थे। आत्मविश्वास 3 कीवर्ड हिट पर उच्च और 2 पर मध्यम रहता है, जो कीवर्ड स्कोर से लिया जाता है, न कि बढ़े हुए स्कोर से। रोल वेट नहीं बदलते हैं। आत्मविश्वास सीमाएँ नहीं बदलती हैं। कैलिब्रेशन रिपोर्ट कीवर्ड कटऑफ को देखने का सुझाव दे सकती है। रोल ओएस उस सुझाव को लागू नहीं करता है।

`ROLEOS_NO_CALIBRATION=1` बढ़ावा बंद कर देता है। रिकॉर्डिंग जारी रहती है।

```bash
roleos calibration
```

किसी भी परिणाम लेज़र के बिना एक निर्देशिका में, यह प्रिंट करता है:

```
no recorded runs yet
```

`roleos route --verbose` और `roleos explain` बढ़ावा, रन गणना और स्वच्छ दर प्रिंट करते हैं जब लेज़र में वे होते हैं। [हैंडबुक](https://mcp-tool-shop-org.github.io/role-os/handbook/calibration/) देखें।

### विचार मंथन मिशन

यह "एआई विचार मंथन" नहीं है। विचार मंथन मिशन **कानून के तहत विशेष भूमिकाएँ हैं, जिसमें ट्रैक किए जा सकने वाली असहमति और निष्कर्ष देने वाला आउटपुट होता है।**

```bash
roleos run "explore product directions for a developer tool discovery platform"
# → MISSION: Brainstorm (Structured Inquiry)
#   Chain: 4 Analysts (parallel) → Normalize → Cross-Examine → Rebut → Synthesize → Expand → Judge
```

**यह इसे अलग कैसे बनाता है:**

- **लेयर 1 (सत्य):** चार विश्लेषक रोल-नेटिव स्कीमा (कॉन्टेक्स्टमैप, यूजरवैल्यूमैप, मैकेनिक्समैप, पोजिशनिंगमैप) उत्सर्जित करते हैं - साझा गद्य नहीं। प्रत्येक भूमिका ब्लाइंडस्पॉट-प्रवर्तित है: निषिद्ध वाक्यांश, निषिद्ध दावा प्रकार, फ़िल्टर्ड इनपुट विभाजन। परमाणुओं में उत्पत्ति होती है। एक निर्देशित क्रॉस-परीक्षा ग्राफ लक्षित चुनौतियाँ उत्पन्न करता है। मूल विश्लेषक दबाव में बचाव, संकुचित या वापस लेते हैं।

- **लेयर 2 (रेंडर):** पांच अलग-अलग मानव आवाजें (बाउंड्री मेमो, फील्ड नोट्स, सिस्टम स्केच, दावा संक्षिप्त, क्रॉस-परीक्षा प्रतिलेख) शाब्दिक प्रतिबंधों के साथ जो आवाज अभिसरण को रोकते हैं। संश्लेषण सत्य का उपभोग करता है, कभी भी रेंडर किए गए गद्य का नहीं। दोनों परतें हमेशा उपलब्ध होती हैं।

- **कस्टडी की श्रृंखला:** रेंडर किए गए प्रत्येक वाक्य का पता सत्य-परत परमाणु तक लगाया जा सकता है। संश्लेषण दिशाएँ परमाणुओं का हवाला देती हैं। क्रॉस-परीक्षा वास्तविक दावा आईडी को लक्षित करता है। विवाद ग्राफ उत्पाद है, गद्य नहीं।

### गहन ऑडिट मिशन

यह एक सतही स्कैन नहीं है। गहन ऑडिट मिशन **एक रिपो को बाध्य घटकों में विघटित करता है और रिपो के अपने निर्भरता ग्राफ द्वारा निर्धारित पैमाने पर विशेषज्ञ ऑडिटर भेजता है।**

```bash
roleos run "deep audit this repo" --manifest=audit-manifest.json
# → MISSION: Deep Audit (Manifest-Scaled)
#   Steps: Component Auditor ×6 + Test Truth Auditor ×6 + Seam Auditor ×8 + Synthesizer + Action Plan + Critic = 23 steps
```

**यह इसे अलग कैसे बनाता है:**

- **गतिशील वितरण** - कार्यकर्ता गणना निश्चित नहीं है। 10-घटक रिपो जिसमें 5 सीमा क्लस्टर हैं, 28 चरण उत्पन्न करते हैं (2×10 + 5 + 3)। 3-घटक रिपो 12 उत्पन्न करता है। स्केलिंग सूत्र `2N + K + 3` है जहाँ N = घटक, K = सीमाएँ।
- **मैनिफेस्ट-समर्थित पार्सल** - एक `audit-manifest.json` घटकों (फ़ाइल पथ, पंक्ति गणना, विवरण के साथ) और सीमाओं (इंटरफ़ेस विवरण के साथ/से) को परिभाषित करता है। प्रत्येक ऑडिटर को केवल अपना पार्सल प्राप्त होता है।
- **चार भूमिका प्रोटोटाइप** - घटक ऑडिटर (प्रति मॉड्यूल कोड सत्य), टेस्ट ट्रुथ ऑडिटर (जो परीक्षण सिद्ध करते हैं बनाम जो मौजूद हैं), सीम ऑडिटर (निर्भरता ग्राफ से एकीकरण सीमाएँ), ऑडिट सिंथेसाइज़र (सभी पार्सल से रैंक किया गया निष्कर्ष + कार्य योजना)।
- **प्रत्येक चरण पर कलाकृति सत्यापन** - `validateArtifact()` दोनों निष्पादन पथों में प्रत्येक चरण के पूरा होने पर सक्रिय होता है। परिणाम चरण वस्तुओं से जुड़े होते हैं। सिस्टम जानता है कि प्रत्येक कलाकृति ने अपने अनुबंध को पूरा किया या नहीं।
- **ईमानदार आंशिक** - जब बजट या दायरा पूरा होने को रोकता है, तो प्रति-घटक निष्कर्ष व्यक्तिगत रूप से मान्य होते हैं। सिस्टम जो कुछ भी पूरा किया गया है, उससे संश्लेषित करता है, कभी भी पूर्ण कवरेज का दिखावा नहीं करता है।

**सिद्ध:** रनर-नेटिव प्रूफ रन - वास्तविक मैनिफेस्ट के खिलाफ 18 परीक्षण, एस्केलेशन री-ओपनिंग और आंशिक विफलता सहित पूर्ण जीवनचक्र सत्यापित। 3/6/10/15-घटक मैनिफेस्ट के लिए स्केलिंग सूत्र सत्यापित।

### डॉगफूड झुंड मिशन

यह एक-पास लिनटर नहीं है। डॉगफूड झुंड मिशन **एक मल्टी-पास कन्वर्जेंस प्रोटोकॉल चलाता है जो एक रिपो को तीन स्वास्थ्य चरणों और पुनरावृत्त फ़ीचर डिलीवरी के माध्यम से "काम करता है" से "उत्पादन-तैयार" तक ले जाता है।**

```bash
roleos swarm
# → MISSION: Dogfood Swarm (Multi-Pass Convergence)
#   Stages: Health-A → Health-B → Health-C → Feature → Final
#   Domain agents: 3-5 parallel per wave (exclusive file ownership)
```

**यह इसे अलग कैसे बनाता है:**

- **तीन-चरणीय स्वास्थ्य जांच** — चरण ए में बग और सुरक्षा संबंधी समस्याओं को ठीक किया जाता है (जब तक 0 गंभीर + 0 उच्च प्राथमिकता वाली समस्याएं हल न हो जाएं)। चरण बी में सक्रिय रूप से सुरक्षा को मजबूत किया जाता है (उपयोगकर्ता निष्कर्षों की समीक्षा करते हैं)। चरण सी में कोडबेस को उपयोगकर्ता के अनुकूल बनाया जाता है — त्रुटि संदेश जो उपयोगकर्ताओं की मदद करते हैं, पुन: कनेक्शन प्रतिक्रिया, लोडिंग स्थिति, पहुंच क्षमता। प्रत्येक चरण एक अलग दृष्टिकोण है, यह एक ही स्कैन को दोहराने जैसा नहीं है।
- **विशिष्ट फ़ाइल स्वामित्व** — प्रत्येक डोमेन एजेंट `swarm-manifest.json` के माध्यम से विशिष्ट फ़ाइलों का मालिक होता है। कोई भी दो एजेंट एक ही फ़ाइल को संपादित नहीं करते हैं। कोई विलय संघर्ष नहीं। कोई समन्वय संबंधी अतिरिक्त बोझ नहीं।
- **बिल्ड गेट** — प्रत्येक चरण के बाद लिंट, टाइपचेक और परीक्षण सफल होना चाहिए। सिस्टम स्वचालित रूप से बिल्ड सिस्टम (नोड, रस्ट, पायथन, गो) का पता लगाता है और सही कमांड चलाता है।
- **उपयोगकर्ता जांच बिंदु** — स्वास्थ्य-बी और सुविधा जांच के लिए निष्पादन से पहले स्पष्ट उपयोगकर्ता अनुमोदन की आवश्यकता होती है। सिस्टम निष्कर्ष प्रस्तुत करता है, और उपयोगकर्ता यह तय करता है कि क्या बनाना है।
- **पुनरावृत्तीय अभिसरण** — चरण तब तक दोहराए जाते हैं जब तक कि निकास शर्तें पूरी नहीं हो जातीं या अधिकतम पुनरावृत्तियों की संख्या तक नहीं पहुंच जाती। प्रत्येक चरण पिछली त्रुटियों के कारण होने वाली समस्याओं को पकड़ने के लिए शुरुआत से फिर से ऑडिट करता है।
- **डोमेन स्वचालित पहचान** — `roleos swarm manifest --generate` रिपॉजिटरी प्रकार (सीएलआई, वेब, डेस्कटॉप, एमसीपी, मोनोरेपो) का पता लगाता है और गैर-अतिव्यापी डोमेन असाइनमेंट उत्पन्न करता है।
